# PS4 unlock host

A static exploit host for a PlayStation 4, with one screen and one button. It
reads the firmware from the console's own user agent, picks the folder that
carries offsets for it, and runs the chain. The progress bar reaches 100 only
when the payload is actually running.

> **Read this first.** Educational use, on hardware you own. See
> [NOTICE.md](NOTICE.md). Running an exploit changes the security state of the
> console, can corrupt its storage, and can get a PSN account banned.

## What it supports

| Firmware | Folder | Chain |
|---|---|---|
| 14.00 – 14.02 | `1400/` | afterglow |
| 13.02 – 13.52 | `1352/` | Slopkit |
| 11.00 – 13.00 | `1300/` | Lapse / Poops |
| 9.00 – 9.60 | `900/` | PSFree |
| 7.00 – 8.52 | `700/` | PSFree |
| 6.72 | `672/` | Lapse |
| 5.05 | `505/` | Lapse |
| 6.00 – 11.02 | `css/` | CSSFontFace |

`index.html` holds the firmware-to-folder table. `ui.js` is the shared progress
screen, `simple.js` adapts the older vendor pages to it, and `icon.png` is
generated by `tools/make_icon.py`.

## Run it on your own network

There is no hosted instance to point at, by design. Host it yourself and give
the address only to the people you want to use it.

### Python, no install

```bash
python3 serve.py
```

It prints the address to open on the console, for example
`http://192.168.1.50:8000/`. Nothing leaves your network.

Use this rather than `python3 -m http.server`: the console only caches the page
for offline use when the manifest is served as `text/cache-manifest`, and the
stdlib default depends on the machine's `mime.types`. `serve.py` sets it
explicitly. A wrong type fails silently — the page works while the network is
up and dies when it is not.

### Docker

```bash
docker compose up -d --build
```

Then open `http://<this-machine>:80/` on the console. The compose file uses host
networking so the console talks to this machine's own address; on Docker Desktop
swap it for the `ports` mapping, commented in the file.

Or without compose:

```bash
docker build -t ps4-unlock-host .
docker run -d --name ps4-unlock-host --network host ps4-unlock-host
```

### Raspberry Pi or any small box

Either of the two above works as-is on a Pi. For something that survives a
reboot without Docker, copy the folder to the machine and run it as a service:

```ini
# /etc/systemd/system/ps4-unlock.service
[Unit]
Description=PS4 unlock host
After=network-online.target

[Service]
WorkingDirectory=/opt/ps4-unlock-host
ExecStart=/usr/bin/python3 serve.py 80
Restart=always
User=pi

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl enable --now ps4-unlock
```

### On the console

Open the address in the PS4 browser and press **Unlock**. The first visit saves
the files for offline use, which is what lets the same page work later without
the server — worth doing once on a stable connection.

## Keeping it to yourself

The server binds to every interface on the machine it runs on, so anyone who can
reach that address can use it. To limit that:

- keep it on your LAN and do not forward a port to it from the router;
- if you need it to survive outside your network, put it behind a VPN — Tailscale
  or WireGuard — rather than publishing it;
- give out the LAN or VPN address, and change the port if you want to be less
  findable.

### A domain name is not a lock

This is the part worth reading twice, because it is a common misunderstanding:

- A hostname only decides **where** a request is sent. It does not decide **who**
  may send one.
- A public DNS record is public. Anyone can resolve it, and anyone who learns the
  name can reach whatever it points at.
- So pointing your own domain at this server does not restrict it to the people
  you choose. It does the opposite: it gives the server a stable, guessable,
  publicly listed address.
- This repository therefore ships no domain and no CNAME. Only its own
  `github.io` address exists, and that is the default for any public repository.

To actually restrict access, restrict it at the network, not at the name:

| Want | Use |
|---|---|
| Only people you choose | Tailscale (or WireGuard) — share the machine, not the internet |
| Only your home | LAN address, no port forwarding |
| Only some devices | Firewall rule or VLAN that allows those MACs/IPs to the port |
| Nobody but you | Bind to `127.0.0.1` and reach it through an SSH tunnel |

A private repository does not help here either: GitHub Pages on a free account
is public regardless, and a private repo needs a paid plan to serve Pages at all.

### Sharing with one or two people

The simplest arrangement that is actually private:

1. Put the host on a small machine at home (a Pi is enough).
2. Install Tailscale on that machine and on your friend's device.
3. Share only that machine, or only the port, through Tailscale.
4. Give them the Tailscale address. It resolves nowhere on the public internet.

That is a real boundary. A hostname is not.

## Validation

Every push and pull request runs `.github/workflows/validate.yml`:

```bash
python3 tools/check.py      # structure, links, manifests, chain DOM, syntax
python3 tools/selftest.py   # proves check.py still catches each known failure
```

`check.py` cannot tell whether an exploit still works on a console — nothing
outside a console can. It catches what an edit tends to break, and what a
console reports as a blank screen or a dead button:

- a manifest caching a file that no longer exists
- a link to a renamed page
- a chain page missing an element its script writes to by name
- a route sending a firmware to a folder whose offset table lacks it
- a payload blob lost or emptied in a merge
- a syntax error, in a file or in an inline script

Green means the host is intact, not that a firmware is exploitable.

## Cache

The console caches aggressively, so each folder carries an HTML5 application
cache manifest. Editing a file without bumping its manifest leaves consoles on
the old copy — the manifest itself must change for the browser to refetch.
`1400/make-manifest.sh` rebuilds its own from content hashes.
